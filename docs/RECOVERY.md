# 送信結果が未確定のとき

タイマー実行で未確定の行が残ると、送信先へ「停止通知」が毎日届きます。停止通知は要約メールではなく、配信IDを含みません。受信箱で配信IDを検索するときに停止通知が見つかっても、要約メールが届いた根拠にはなりません。

送信要求の前に止まった場合（記事履歴の保存失敗・時間上限など）は、コードが自動で`CANCELLED`にします。詳細欄に「送信要求前に停止したため自動で取消（未送信）」と残ります。この行に手作業は不要です。

## 先に停止する

`removeDailyTrigger`で日次実行を止めます。手動送信も重ねて実行しないでください。メール履歴の未確定行は削除せず、本文・記事キーJSONを保全します。

## 状態の意味

| 状態 | 意味 | 次回の実送信 |
| --- | --- | --- |
| PREVIEW | プレビュー。送信していない | 妨げない・記事も処理済みにしない |
| PREPARED | 本文保存済み。送信要求開始前 | 停止する |
| SENDING | 送信要求開始を記録済み。完了記録なし | 停止する |
| UNKNOWN | 送信時に例外。実際の送信有無は未確定 | 停止する |
| SENT | MailApp正常終了、または本人が送信を確認 | 記事キーの重複を除外して続行 |
| CANCELLED | 本人が未送信を確認して取り消した、またはコードが送信要求前の停止を自動で取り消した | 記事は次回取得範囲にあれば再び候補になる |

「状態」列にはプルダウンが付いています（`setupSheets`実行時に設定）。一覧にない値は入力できません。

## 確認と確定

1. Apps Scriptの「実行数」で当該実行が終了していることを確認します。まだ実行中の行を変更しないでください。
2. `メール履歴`の配信ID・宛先・件名・本文を確認します。
3. 宛先の受信箱・迷惑メール等で、その配信IDを含む件名を検索します。送信元の送信済みフォルダーに必ず保存されるとは限りません。
4. 受信等で送信を確認できた場合だけ、「状態」を`SENT`にし、「送信日時」と「詳細」に本人確認の根拠を記録します。「記事キーJSON」は変更しません。
5. `PREPARED`のまま実行が終了していれば、送信要求前に停止しています（自動取消の記録にも失敗したか、GASの実行時間上限で強制終了した場合です）。未送信を確認して`CANCELLED`にし、詳細へ理由を残します。
6. `SENDING` / `UNKNOWN`で送信有無を確認できない場合は、そのまま残します。未着だけを根拠に即時再送しないでください。遅配の可能性があります。
7. 本人が未送信と判断できた場合に限り`CANCELLED`にし、次回の候補化を許可します。
8. 未確定行がなくなったら、必要に応じて手動確認後に`installDailyTrigger`を実行します。

`記事履歴`は本文の参照用です。重複判定の根拠は`メール履歴`の`SENT`行と記事キーJSONです。CANCELLEDの配信IDに紐づく記事行が残っていても、送信済みを意味しません。

## その他の停止

- モデルやAPIキー不備：スクリプトプロパティを確認。キーの値をログや問い合わせ本文に貼らないでください。
- RSS取得失敗：URLがRSS/Atomであるか、認証やアクセス制限がないか確認。取得制限を迂回しません。
- 要約失敗：実行履歴に`GEMINI_HTTP_429`などの分類が残る場合があります。詳細なAPI応答本文はキー露出防止のため保存しません。Google側の利用状況を確認してください。429が続く場合は`配信設定`の「要約間隔秒」を増やすか、最大記事数を減らします。`GEMINI_HTTP_400`が出始めたら、思考設定（`GEMINI_THINKING_BUDGET` / `GEMINI_THINKING_LEVEL`）がモデルに合っているか確認します。
- 時間上限で一部だけ送信：実行履歴とメール履歴の詳細に「残りN件は次回候補」と残ります。毎回出る場合は思考設定で応答を速くするか、最大記事数を減らします。
- 停止通知が届かない：`配信設定`の「停止通知」がTRUEか、メール送信枠が残っているかを確認します。
- シートの列見出し変更：元の見出し・順番を復元します。既存データを削除して初期化しないでください。
- 複数利用者・複数コピーでの実行：このロックは同じスクリプト内だけです。同じ宛先へ複数のコピーを動かすと重複する場合があります。

コードには受信箱の自動照合・不確定メールの自動再送機能を設けていません。自動で取り消すのは、送信要求の前に止まったと確実に分かる場合（上記の自動`CANCELLED`）だけです。

## 通知履歴と記録警告

停止通知・記録警告の実際の本文は`通知履歴`に送信前に保存します。状態は次のとおりです。

| 状態 | 意味 |
| --- | --- |
| PREPARED | 本文を保存済み。送信要求前（実行が強制終了した場合などに残る） |
| SENDING | 送信要求開始を記録済み。完了記録なし |
| CANCELLED | 送信要求の前に失敗したため未送信が確実 |
| UNKNOWN | 送信処理で例外、または送信処理後の記録に失敗。送信有無を断定できない |
| SENT | 通知の送信処理が正常終了 |

本文を保存する前に失敗した場合は行を作らず、実行履歴に「通知未送信」と残します。同じ通知を自動再試行しません。通知履歴は記事の重複判定には使わず、通知が未確定でも要約配信はブロックしません。翌日の実行でも停止する場合は別の通知が作られます。

「記録警告」は、要約メールの送信処理は正常終了したのに、メール履歴の`SENT`記録に失敗した場合の通知です（実行履歴だけの保存失敗では通知しません）。メール履歴がSENTなら、要約メールを再送しないでください。SENDING等が残った場合は上記の受信確認手順で状態を確定します。実行履歴の保存自体が失敗すると、実行履歴に記録が残らないこともあります。メール履歴と通知履歴を併せて確認してください。

通知本文を事前保存できない場合、`通知履歴`シートがない場合は通知を送信しません。シートがないときは`setupSheets`を実行してください。シート自体にアクセスできない場合、設定読込み前のエラー、GAS強制終了、メール送信枠不足などでも通知できない場合があります。通知の到着だけを稼働監視の根拠にしないでください。

APIが60秒より長いRetryInfoを指定した場合や、指定時間（RetryInfoまたは5秒→15秒のバックオフ）を待つ余裕がない場合は、早く再試行せず残りの記事を次回候補へ回します。配信設定の「要約間隔秒」を短くしても、API指定待機は短縮しません。


## 1.1.3の最終試行後の待機指定

3回目の試行でも429/5xxとRetryInfoが返った場合は、後続記事へのGemini要求をその回では行いません。短い待機指定でも次回候補へ延期します。完了済みの要約だけを送信し、未完了記事は送信済みとして記録しません。
